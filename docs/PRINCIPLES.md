# 品味与手法（灵魂篇）

> 机制、约束、命令在别的文档里。**这一篇记的是"为什么这样做才对"**——
> 重置之后最容易一起丢掉的东西：判断取向、被否掉的方案、以及"什么算做好"。
> 开工先读这里，再读 `AGENTS.md`。

## 0. 一句话

这是一个**冷峻、克制、可信**的都市生存游戏。玩家在信息不全的情况下做取舍，
UI 的职责是**如实、安静、不挡路**地把他掌握的一切摆出来。

## 一、产品品味（做取舍时的取向）

1. **交互靠常理，不靠说明书。**
   拖进去的就能拖回来；点一下的地方就别再加一个"撤销"。
   反例：给上交槽加一个「取回」按钮 → 正解：把槽内物资**拖走**即取回。
2. **不擅自加限制。**
   没写有限制的技能就是没限制；没声明的机制不要"顺手"补上。
   反例：给所有主动技能补"每回合 1 次" → 正解：限制必须由内容**显式声明**（`AbilityDefinition.per_turn`），引擎只对声明者生效。
3. **信息要能看，不要被挡。**
   一切"查看"类操作（点空气、开房客卡、看日志、点吐司本身）都放行；
   阻断只用于**必须做的决定**，而且提供的是**隐藏 / 显示**，不是**取消**。
   反例：发现界面放"取消" → 正解：不可反悔，但可随时收起看场面。
4. **状态必须如实。**
   证伪就是"已证伪"，封印就是"已封印"，没生效就是没生效。
   绝不用一个近似值冒充真相（例如用"羁绊等级 0"冒充"性格失效"）。
5. **克制、统一、MC 风。**
   暗绿底 + 琥珀；动效只做悬停变色/吐司上滑/轻微渐变；
   新按钮**复用既有参数**（`.btn` / `.btn.p`），不另起一套样式。
6. **表现层要"稳"。**
   宽度/高度/行高固定，长文本 `nowrap + ellipsis`，不因字体差异而错乱；
   同一流程的不同步骤**同宽**，避免弹窗忽大忽小。
7. **文案属于内容层。**
   提示语/标题/选项名/标签/机制说明，一律由内容层随视图/状态下发；
   系统与前端**只渲染，不写死**。
8. **世界观语气：冷、准、生活流里透诡异。**
   写内容时少用感叹与解释，多用具体细节（声音、气味、时间、半句话）；
   恐怖来自"不对劲"，不是来自形容词。

## 二、工程手法（怎么改，才不越改越乱）

1. **先复现，再找根因，在正确的层修。** 不修症状、不打补丁式特判。
2. **普适规则要删特例、留一条公共路径。**
   一条规则若对全体成立，就删掉所有 `if 特例`，用一个公共函数/入口表达；
   **不要用"排除名单"反着描述普适规则**。反例：给休克、创伤、情绪各写一份 `-1`，再互相排除；
   正解：`condition` 回合末统一走一个 `layers-1` 公共函数，永续/自管只在定义上声明。
3. **机制进后端，而且调用后端既有方法。**
   搬逻辑时用引擎/内容的现成入口（如 `engine._bond_tier`），
   **绝不把前端的近似算法抄进后端覆盖它**。
4. **前端只做展示。**
   不排序、不判档位、不判目标合法性、不算概率、不决定顺序；只渲染后端字段。
5. **内容优先，零改核心。**
   新东西放 `data/` 或 `dlc/`，靠自动发现 + 声明式规格生效。
6. **改动要可核验。**
   批量改动用脚本做**条件替换 + 断言替换次数**；改完 grep 复核；
   注意导入作用域（模块级 vs 函数内——写错就是运行期 `NameError`）。
7. **每次都验证，并区分"我验证过"和"应该没问题"。**
   固定动作：`compileall` → 单测 → `validate_content` → `audit_separation` → 前端 `node --check` →
   无头浏览器/CDP 实测 → 压测。**起服务看 traceback**，不要凭猜。
8. **测试是规格。**
   平衡/设计改动会打破写死旧数值的测试——**更新测试**，而不是迁就旧值。
9. **只清自己产生的东西。**
   存档/运行期目录用环境变量隔离（`WEIREN_SAVES_DIR`），绝不批量删用户文件。
10. **文档只写规则，不复制清单。**
    注册表、字段名、文件名、性格键、目录树这类清单，一律指向唯一来源（代码或单一文档）；
    规则文档里复制的清单一定会和代码漂移。**反例**：在 skill 里重新列一遍八种性格、注册表、
    系统文件范围——正解：写"以 `X` 为准"。

## 三、判断样例（反 → 正）

- 反：档位在前端按 `tiers` 复算，系统里再硬编码一份阈值 →
  正：后端 `engine._bond_tier(key, lv)` 出数，前端只把数值映射成颜色/档名。
- 反：把"羁绊没激活"当成"性格失效"，给性格名划线 →
  正：只有 `persona_off`（性格/被动真的失效）才划线；等级 0 只是变暗未激活。
- 反："好像好了"就交付 → 正：起服务、看堆栈、无头复现、给出可复述的验证结果。
- 反：为一个动作堆三个按钮 → 正：一个符合直觉的动作（拖拽/双击/悬停）解决。
- 反：把机制文案写进前端 → 正：内容层下发 `title/prompt/settle/cancel_prompt/...`。

## 四、用户在意什么（语气与期待）

- 要**根因**、要**分层正确**、要**先自己验证过**再下结论。
- 讨厌冗余、讨厌擅自改设计数值/加限制、讨厌"看起来能用"。
- 反馈短而准；一次给多条时**逐条落实**并逐条回报。
- 结论先行，过程简洁；不确定就明说，不要编。
