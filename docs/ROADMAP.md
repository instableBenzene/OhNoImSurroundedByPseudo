# 路线图（想做的系统 · 讨论结论）

> 这份记的是**还没做、但方向已经聊清**的东西。已做的决策在 `docs/DECISIONS.md`，
> 平衡账在 `docs/BALANCE.md`。每条都写明：**现成能复用什么**、**要新造什么**、**动手前必须回答什么**。

## 1. 游戏模式：无尽模式 / 故事模式

**好消息**：两者都不该改核心，而是"一组规则 + 一张表"——符合 `docs/PRINCIPLES.md` §二.5。

- **无尽模式**：游戏永不结束；伪人**不定期重刷**；死亡房客与已解放的伪人**若干回合后回到池子**；看撑多久。
  - 复用：`_finish()` 是唯一的结束口 → 无尽下不调用即可；`_roll_next_pseudo_visit` + `visitor_pool`
    已经是"重刷/回池"的现成通道（拒绝与离开都走过它）；`pseudo.liberated/known/revealed` 重置即为重刷。
  - 要新造：**模式定义**（结束条件 / 重刷间隔 / 回池规则），建议放内容层（`data/`）当"模式表"，
    开局页与「地图」「伪人」并列出一个下拉。
  - 要回答：重刷时**换不换伪人**（同场景重置 vs 换 `scenario_id`）；图鉴/羁绊的账怎么算（死亡回池要不要保留羁绊进度）。
- **故事模式**：本质是**特殊种子**——开局有谁、第几回合发生什么都是固定的；配套**剧情文本**与**角色对话**。
  - 复用：确定性 RNG + `start_choices` + `next_pseudo_turn` 已能复现"何时发生什么"；
    剧情文本走**信息/事件**通道（`kind`/`subtype`/`data` 都在）；展示走既有提醒。
  - 要新造：**按回合排定的剧本表**（如 `STORY_SCRIPT = ((1, …), (3, …))`），由系统在回合开始查表触发。
  - 要回答：剧本表与**全局事件**的关系（建议同构：剧本 = 预置的全局事件，别再造第三套提醒）。

## 2. 对话系统（galgame 式对话框）

**空间问题其实是"层级"问题**，不是"没地方放"：

- **入口**收敛到"**选中房客之后**"——展开卡的标题行，与「指认」同一处（`docs/STYLE.md` §10.3/§10.7 的既有范式）。
  反面教材就是「驱逐」：塞在每张头像脸上，正是因为没有先选中谁。
- **对话框**用**贴底悬浮**（背包 / 外出搜索那种），不用阻塞式弹窗：底部一条，左侧头像走 `avatarIcon()`，
  正文走 `mdText()`（对话换行规则已经就位）。
- **闲聊**不要"从头顶冒气泡"（突兀）——建议**进日志/信息条**：闲聊 = 一条带说话人的可点开日志（多句折在明细里，
  正好复用刚统一的 log 层折叠）；或者作为「现有信息」的一类。
- **契约**：对话内容是内容层声明的（`LINES`/`DIALOGUE`），系统只负责"什么时候问一句、怎么显示"——
  与 `PENDING_VIEWS` 同构，别在系统里写死任何台词。

## 3. 战斗：伪人不设血条，只由**规则**制衡

**这是设计底线，不是待办**：伪人不该有血条，驱逐/解放要像规则怪谈那样用**规则**完成，而不是把数值打到 0——
否则角色强度会退化成"数值比较"，将来必然膨胀。

- 现成骨架就在：**闸门**（`gate`/`NODE_HOOKS`）是纯查询的布尔条件；洋葱的解放（连续无烦躁 / 无生命损失）、
  苯的「早交班」、薯条的「暴露值 ≥25」都是"规则制衡"的实例。将来所谓"战斗"应该是**声明式规则对撞**
  （多个 gate 叠加 + 内容自述反制条件），不是 HP 交换。
- **建议写成硬性约束**（`docs/PRINCIPLES.md` 或本文件当权威）：**伤害可以当规则的输入，但不能当"打到 0"的判据**；
  伪人卡不显示血条；一切"击败"必须能复述成一条可阅读的规则。

## 4. "小兵"型敌人：用现成的概率系统，**不新造血条**

结论（与 DLC 作者的 CoC/DnD 提议对照后）：**这套概率系统就是 CoC/DnD 的判定内核**，所以"战斗"缺的不是数值框架：

| CoC / DnD | 本仓库现成的东西 |
| --- | --- |
| 技能值 + 情境修正 → 掷骰 | `_apply_chance(...)` + 通道 `_apply_modifiers(...)`（`flat/percent/mul/final/max/min`） |
| 修正来自装备/状态/环境 | `path`/`source` 匹配，内容自行声明 |
| 大成功 / 大失败 | 必定 0/100 显式处理；非必定收敛 **5%~95%** |
| 战斗后果 | 创伤 / 紊乱 / 休克 / 情绪（整套已在） |
| 回合与行动次数 | 回合阶段 + 行为次数 |

**只缺两件**：

1. **对抗式判定的公共入口**（现在是双方各自独立掷；需要"我方 vs 对方"的统一规则，别让每个内容各写一套）。
2. **"小兵"的声明方式**：它是**内容层的一类实体**（属性 = 判定阈值，行为 = 既定规则），系统只"照声明跑判定"——
   零改核心（同 `INFORMATION_TEMPLATES` 的路子）。

**必须避免的**：让小兵拥有"独立回合 + 自己的调度/印记/图鉴卡"，那会长成**第二个 `pseudo_system`**
（所有 `_pseudo_*` 的单数假设都要跟着改）。更省的做法：小兵挂在**已有的单数容器**上
（作为伪人场景的一部分、或作为门外事件 / 搜索遭遇），这样"多伪人同局"那条（见 §1 与 `DECISIONS`）
不会和它互相拖累。

**与 §3 底线一致**："打倒"不靠 HP 归零，而是**累积规则条件**（连续判定成功、逐个拆掉它的规则前提……）——
和洋葱解放（连续无烦躁 / 无生命损失）**是同一个形状**。

## 5. 存档结构迁移（与上面几条独立，但迟早撞上）

- 现状：`meta.version` 会写盘、`from_dict` 对未知字段严格报错，但**没有迁移**；
  字段后加（如 `log.entries`）甚至**没升版本号**，于是同一版本号下住着两种结构。
- 要回答：① 什么时候必须升版本（字段增删 vs 语义变化）；② 迁移写在哪层（`from_dict` 逐级升 /
  开局统一跑一遍）；③ 失败时拒读还是"尽力读 + 明确告知缺了什么"。
- 相关踩坑见 `docs/DECISIONS.md`「导出的游戏记录不从第 1 回合开始」。

## 6. 内容包专属系统（这是"小兵战斗"的正确归属）

**定位**：战斗**不是核心系统**，而是**某个资料包自己的专属系统**——就像将来另一个包的专属系统是
"仓库有上限"。核心只提供**通用能力**，包的规则住在包里（`docs/PRINCIPLES.md` §二.5）。

**已经有的挂点**（做专属系统**不需要改核心**）：

| 需要 | 现成机制 |
| --- | --- |
| 包自己的状态（小兵列表 / 战场） | `CONTAINERS = {"<key>": <类>}`（进存档、随包回滚） |
| 包自己的界面 | `PANEL = (build_view, resolve_action)`（核心只"下发视图 + 转发动作"） |
| 什么时候触发 | `NODE_HOOKS` / 任务 / 门外事件 / 搜索遭遇 |
| 判定 | `_apply_chance(...)` + 通道修饰器（`path`/`source` 由包声明） |
| 后果 | 创伤 / 紊乱 / 休克 / 情绪（整套已在） |

**已识别的缺口**：要表达"**仓库有上限**"这类**容量约束**，目前**没有**对应的通道或闸门
（容量由仓储与携带上限直接给出）。建议补一个**容量闸门**（如 `capacity.warehouse` / `capacity.carry`），
让包能"用声明改上限"而不是去改核心；补完记得同步 `docs/ARCH.md` 的闸门目录。

**判据**（将来判定"该不该进核心"）：能被**任意一个包单独提出、单独关掉**的东西 → 属于包；
两个以上包都要用、或涉及存档格式与回合流程的 → 才考虑进核心。

## 7. 语言系统（lang）

**一句话**：语言包 = **一种内容包**（复用"有序清单 + 同名覆盖 + 回落"那套）；真正的工作量在
**把系统层写死的中文句子抽成模板**，不在"支持几门语言"。

### 现状盘点（哪些已经就绪、哪些是硬骨头）

| 面 | 现状 |
| --- | --- |
| 内容层文本（技能名/描述/chips/提示语/标签/图鉴） | **已经天然可分语言**（全在 `data/` 与 `dlc/`，且系统/前端不写死内容名） |
| 界面 chrome（按钮/标题/列名） | 少量写死在 `index.html` ❌ → 需要一张 **UI 词表** |
| 系统层日志句子（约 118 条，`engine.py` / `systems/*`） | ❌ 写死中文 f-string → 需要 **消息模板 + 占位符** |
| 字体与排版 | 已由 `theme.py` 的字体栈 + 资源包控制 ✅（语言包顺带就能换字体） |
| 数字/百分号/负号 | 已统一（阿拉伯数字、`−` 负号）✅ |

### 建议形状

- **目录**：`resourcepacks/<lang>/`? **不**——语言是"内容 + 界面"两层的事，建议独立成
  `lang/<code>/`（`messages.py` 消息模板 + `ui.py` 界面词表 + 可选 `theme` 覆盖字体），
  与 `dlc/`、`resourcepacks/` **并列**、同样**有序**（因为可能"英文 + 术语表"两个包叠加）。
- **取文本统一入口**：系统层只写 **key**，不写句子：`t("log.consume_sanity", name=…, source=…, amount=…)`。
  → 顺手把"系统层写死中文"这条清掉，**也正好和刚统一的 log 层呼应**（见下）。
- **回退链**：语言包 → base 中文；缺 key 就回落，**永不空字符串**。
- **不能翻译的东西**：`id`、数值、以及**修饰器的 `path`/`source` 匹配键**（
  它们参与规则命中，翻译了内容逻辑就断——这是硬边界）。

### 与已有机制的三个交界面（必须一起想）

1. **log 折叠**：现在明细是**按中文形状解析**出来的（`weiren_game/log_shape.py`）——
   一旦多语言，形状表就要按语言各写一份 ❌。
   正解：让值层在**记日志时同时带上结构化数据**（谁/多少/为什么），语言只影响渲染，
   解析器反而可以退休。（这也是"i18n 是推动结构化"的经典理由。）
2. **`tools/audit_text.py`**：它按中文标点判"有没有句号"、按中文词表查含糊词 ❌ → 要按语言参数化
   （`--lang` 或读语言包里的标点/词表）。
3. **`audit_separation.py`**：切语言后仍需全绿 ✅——内容名不得因语言进系统层；
   语言包的"词表"属于**外观/内容层**，系统层只认 key ✅。

### 落地顺序（都不大，按序做）

1. `t()` + `lang/base/messages.py`：先把**系统层那 118 条日志**搬成模板（行为零变化，纯搬运）。
2. 界面 chrome 词表（`index.html` 的写死文案 → 后端下发或前端词表）。
3. 一个真语言包（如 `en`）**只翻界面 + 日志**（内容文本交给内容包自己逐步补），
   用来暴露"英文更长会不会撑破 STYLE §10 那些固定宽高的范式"这个真风险。

**为什么值得做**：它同时解决三件事——① 让朋友的 DLC 能自带语言；② 逼着把系统层的中文句子
结构化（顺带修掉 log 折叠那条"按形状解析"的脆弱设计）；③ 内容/界面/外观三层边界再钉一遍。

### 真正想解决的问题：把"无主文本"收拢（数据见下）

| 面 | 规模（含中文行） | 该不该收拢 |
| --- | --- | --- |
| 内容·技能 / 物品描述（就近写在各自定义里） | 40 文件 / 约 1564 行 | **不动**——它跟着定义走是对的 |
| 内容·风味 / 图鉴文本（`flavor.py`、`items/codex_text.py`、`information_text.py`、`codex_pack.py`、`codex_mechanics.py`、`labels.py`） | 6 文件 / 约 420 行 | 已经是"收拢"的样板 |
| **系统层·日志与报错**（`engine.py` / `systems/*` / `cli.py`） | 15 文件 / **约 922 行** | ✅ **收拢重点** |
| **前端·界面 chrome**（`webui/index.html`） | 1 文件 / **约 670 行** | ✅ **收拢重点** |
| 状态 / 情绪定义里的描述（`condition.py`） | 1 文件 / 85 行 | 中性 |

**判据：收拢 ≠ 集中到一个大文件。**

- **无主文本**（系统日志、报错、界面 chrome）→ 本来就没人管，**该收进词表**：一处能看全、一处能改全。
- **有主文本**（技能/物品/伪人描述）→ **保持在定义旁边**（就近声明是这套架构的立身之本），
  收拢的是**呈递方式**，不是位置：用一张导出表让它们"**一处能看全**"即可。

**第一步（零风险、立刻见效）**：`tools/dump_text.py` —— 把所有面向玩家的文本导成一张表
（来源文件 / key / 文本 / 长度），既满足"收拢"的体感，又正好是 lang 的**底表**；
搬运（`t()` 化）在它之后按表逐块做，才不会边搬边漏。

### 查重结论（全库 3276 条引号文本、只取 ≥8 汉字的成句文本 → 2017 条 / 23 组重复）

**重要前提：字符串分三类，只有第一类才是"文案"。**

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| **① 玩家可见文案** | 「请先选择一个存档。」「高生命值自然流失」（其实是键）… | 查重有意义 |
| **② 数据键**（`path`/`source`/tag/性别/年龄/兴趣） | 「伪人使用主动能力」x15、「回合末消耗」x26、「男性」x16 | **必须全库一致、且禁止翻译**——重复是对的 |
| **③ 开发文本**（docstring / 注释） | 「序列化为普通字典。」x17、「返回事件名对应的 `EVENT_IDS` 编号。」x10 | 与玩家无关，可忽略（或按代码风格收拢） |

**① 类里真正值得动的，只有十来组，且分三种病**：

- **系统 / 前端 chrome 重复**：「请先选择一个存档。」×3、「请先完成当前选择。」×2（都在 `index.html`）
  → 抽成一个 key，一处改全。
- **同一句话"内容层 + 系统层"各写一遍**（**违反 `PRINCIPLES` §一.7：文案属于内容层**）：
  - 「下一次访客来访被取消。」（厄瑞玻斯牌面文案 vs `visitor_system` 日志）
  - 「指认房间内的伪人」（伪人模块的信息文案 vs `information_system` 的标题）
  - 「宽敞明亮的品牌直营店，产出顶配防具。」（`codex_pack` vs `locations.py` 的地点描述）
  → 该**由内容声明、系统引用**，而不是两边各写。
- **同一概念多处手写**：「我不能没有购物袋」在 `tear.py` 里出现 3 次（技能名 / 描述 / 图鉴）
  → 该**从定义派生**（`A(...)` 的 name 就是唯一真源）。
- 系统层同类报错的重复（「该格没有这件物资。」×2、「目标格超出该房客的携带栏范围。」×2、
  「{}每局仅能使用一次。」×2 …）→ 同一个函数的两条分支，**合一个常量**即可。

**结论**：文案重复**不严重**（十来组，且多是"内容 vs 系统"的边界问题），所以 lang 的价值主要在
**收拢无主文本（922 + 670 行）+ 逼出这些边界违规**，而不是"消掉大量重复字符串"。

### 术语 / 句式一致性（同一概念被写成几种说法）

`docs/STYLE.md` §11 已定规则：**一个概念全库只用一个词**，且"权威是代码里稳定的那批、不另列清单"。
问题在于**没有机检**，于是随手写的少数派会长期潜伏（实测：语料 990 条成句文本）：

| 词族 | 多数派 | 少数派（漂移） |
| --- | --- | --- |
| 理智 / 理智值 | 理智 217 | 理智值 **10** |
| 生命 / 生命值 | 生命 203 | 生命值 **19** |
| 消耗 / 流失 / 损失 / 扣除 / 失去 | 消耗 227、流失 35 | 损失 **10**、失去 **4**、扣除 **3** |
| 免疫 / 抵御 / 不受 / 免受 | 免疫 32、抵御 26 | 不受 6、免受 **1** |

**判据（很好用）**：**少数派才是漂移**——出现 10 次以内的写法多半是最近随手写的；
出现上百次的才是稳定用法。所以要做的不是"统计哪个词更雅"，而是**把少数派改齐多数派**
（或反过来，如果作者想换一套说法）。

**做法**：把它做成 `tools/dump_text.py` 的一部分（同一份语料、同一张表）：
① 词族计数（上面这张表）；② 列出少数派的**每一处**（文件:行 + 原句），好逐条改；
③ 可加"的 / 主动被动"这类粗粒度风格指标（如「的」密度、被动句「被…」占比），只做提示、不做判据。
**不写进 STYLE 的清单**（避免和代码漂移）——STYLE 只保留"一个概念一个词"这条规则，词表由脚本现算。
