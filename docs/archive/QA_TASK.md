# 项目系统性 QA 与局部视觉升级任务说明（给 AI Agent）

> 适用对象：在本仓库工作的代码 Agent / 开发者。
>
> **一句话定位**：这是一次「在已基本完成的游戏上做系统性 QA + 局部视觉升级」，
> **不是重新设计游戏**。
>
> **最重要的硬约束**：SVC 只负责让**物品 / 房客 / 伪人 / 地点 / 状态等游戏资源**更精致、更统一；
> 已经调试满意、确认保留的 **UI（按钮、选项框、卡片、面板、边框、间距、字体布局、交互区域、配色、整体结构）
> 全部保持原样**。除非发现明确 Bug，否则 UI 视为已冻结设计。

请基于当前项目现有代码、`*.md` 设计文档、`tests/` 文件夹以及网页实际运行效果，对项目进行一次系统性的
**美术资源、测试体系、网页端自动化测试、文本/实际效果一致性、代码架构符合性**检查与增强。

本次工作重点**不是重做 UI**，而是在**保留当前已经调试完成且满意的 UI 基础上**做局部优化与测试增强。

## 一、美术资源与 SVC 图标优化

目前整体 SVC 风格方向已经基本确定，希望继续优化游戏中的：

- 物资图标
- 房客图标 / 人物小图
- 伪人图标
- 地点图标
- 状态图标
- 其他游戏内小型视觉资源

目前的问题：**部分简笔画仍然过于简陋，接近简单几何符号的直接拼接。**

需要提升设计感，使其符合既定的 SVC 视觉语言：

- 以线条、轮廓、几何构图为主要表现形式
- 低填充，而不是大量色块
- 统一线宽与视觉比例
- 保持小尺寸下的辨识度
- 使用经过设计的符号，而不是直接使用 Emoji
- 适当加入能体现人物 / 物品特征的结构细节
- 不追求写实，但也不能像临时画出来的占位图
- 让不同角色、物品之间拥有统一的视觉语法
- 颜色主要用于品质、状态、危险等信息表达，而不是主要造型手段

**可以参考提供的 SVC 风格参考图来优化图标。**

> **注意**：参考图仅用于参考图标 / 角色 / 物品的视觉表现方式，**不允许借此修改现有 UI**。

- 选项框

- 间距

- 交互区域

> 本次 SVC 优化**只针对 UI 内部所使用的图标、人物、物品、地点等视觉资源**。
>
> 换句话说：**优化图标，但不要动 UI。**

## 三、主页面背景优化

在**保持现有 UI 布局、按钮、选项框与其他 UI 元素完全不变**的前提下，可单独考虑优化
**主页面 / 游戏主场景的背景视觉表现**。背景需与 SVC 风格协调，但不能喧宾夺主。

希望达到：

- 有明确的空间感
- 有避难所 / 房屋 / 夜间环境的氛围
- 与游戏「伪人、生存、观察、怀疑」的主题相符
- 比目前更完整、更有场景感
- 但不要过度写实
- 不要让背景抢走 UI 信息
- 不要影响文字与按钮的可读性

重点：**背景可以重新设计，但 UI 不要跟着重做。**

## 四、优化 `tests/` 测试体系

完整检查当前 `tests/` 中的测试代码，重点判断：

1. 当前测试覆盖了哪些系统？
2. 哪些核心系统实际上没有被测试？
3. 哪些测试只测了「正常情况」？
4. 哪些边界条件没有覆盖？
5. 哪些测试容易出现假阳性 / 假阴性？
6. 测试是否真正验证了游戏规则，而不只是「函数能跑」？
7. 测试之间是否存在重复？
8. 是否存在应拆分、重构或参数化的测试？
9. 是否应增加随机性测试、状态组合测试、回合流程测试？

尤其关注核心系统：房客、访客、伪人、信息系统、状态变化、物品、搜索、资源消耗、回合推进、
门口事件、技能、DLC、存档 / 读取、随机事件、胜负条件。

请在**不改变游戏设计规则的前提下**完善测试体系。

## 五、模拟真实网页端操作，进行尽可能智能的 Bug 测试

不要只依赖单元测试，要尽可能模拟真实玩家在网页端的操作流程，做自动化 / 半自动化测试。

### 基础操作

- 点击按钮
- 选择房客
- 接待访客 / 拒绝访客
- 指派搜索
- 使用物品
- 查看信息
- 切换界面
- 推进回合
- 保存 / 读取 / 开新局

### 异常操作（重点）

- 连续快速点击
- 重复点击同一个按钮
- 在状态变化瞬间点击
- 没有资源时继续操作
- 背包已满时获得物品
- 对死亡 / 异常角色进行操作
- 在错误阶段点击其他阶段的按钮
- 重复提交同一个动作
- 保存 / 读取过程中进行操作
- 刷新页面
- 快速切换界面
- 多次执行同一个事件

### 状态组合

尽可能覆盖：**不同房客 × 不同状态 × 不同物品 × 不同回合 × 不同事件**。

特别寻找正常测试难以发现的：状态覆盖、状态冲突、数值异常、UI 与游戏状态不同步、数据残留、
重复触发、一次操作触发多个事件、应该触发却没触发、不应该触发却触发。

## 六、尽可能进行「智能探索式」测试

不要只按固定脚本（点击 A → B → C），测试系统应能**根据当前页面状态动态决定下一步**：

```text
读取当前页面
    ↓
识别当前阶段
    ↓
识别当前可操作元素
    ↓
随机 / 策略选择一个合理操作
    ↓
执行操作
    ↓
读取页面变化
    ↓
检查游戏状态
    ↓
发现异常？
 ┌──是──→ 记录操作路径 + 状态 + 错误
 ↓
否
 ↓
继续探索
```

通过大量不同操作路径发现隐藏 Bug。同时避免无限随机点击，应具备：

- 操作记录
- 状态记录
- 操作去重
- 异常回溯
- 错误复现路径
- 测试超时
- 最大操作次数
- 页面状态检测

发现 Bug 时，记录：

```text
Bug：
复现步骤：
测试前状态：
执行操作：
预期结果：
实际结果：
涉及系统：
是否可以稳定复现：
```

## 七、比较「文本效果」与「实际网页效果」

将代码 / `.md` / 配置文件中描述的游戏设计，与实际网页运行结果对照，重点检查：

> **「设计文档说应该发生什么」 vs 「实际游戏发生了什么」。**

例：

```text
设计文档：访客出现 → 玩家可以接纳 / 拒绝
实际：访客出现 → 是否真的存在对应按钮？按钮是否在正确阶段出现？点击后状态是否正确变化？
```

```text
设计文档：物品数量 -1
实际：物品数量是否真的 -1？UI 是否同步？背包数据是否同步？保存后是否仍正确？
```

重点寻找四类问题：

1. **文本正确、实际错误**：文档 / 代码逻辑看似正确，但网页实际行为错误。
2. **实际正确、文本错误**：代码已实现，但 `.md` 仍是旧逻辑。
3. **两边都不完整**：设计与实现都存在缺口。
4. **表面正确、边界错误**：普通情况正常，特殊条件下出问题。

## 八、检查总体代码是否符合 `.md` 中的设计思路

把项目中的 `.md` 作为当前设计依据，检查整体代码结构与实际实现。

重点不是检查「有没有这个函数」，而是检查 **代码实现是否真正遵循设计文档中的系统思路**。

重点检查：核心数据结构、房客系统、伪人系统、信息系统、事件系统、状态系统、物品系统、回合系统、
搜索系统、DLC 系统、存档系统、UI 与游戏逻辑的分离、随机事件、状态机 / 阶段控制、数据驱动设计。

如果发现：

```text
.md 设计：A → B → C
代码：    A → C
```

需要明确指出这种差异。如果代码能运行但已偏离原本的架构思想，同样要指出。

**不要为了让代码「看起来符合」而修改设计文档。** 应先报告：

> 文档设计 → 当前实现 → 差异 → 风险 → 建议。

## 九、修改原则（优先级）

| 优先级 | 原则 |
| --- | --- |
| **P0** | **不能破坏现有功能**：不因重构测试或优化资源而破坏游戏逻辑 |
| **P1** | **不能破坏已确认的 UI**：除非明确 Bug，否则按钮 / 选项框 / 卡片 / 面板样式不要改 |
| **P2** | **提高测试覆盖率**：尤其是实际网页操作与边界情况 |
| **P3** | **修复实际发现的 Bug**：能确定的直接修，并补对应测试 |
| **P4** | **优化 SVC 图标**：只优化人物 / 物品 / 地点 / 状态 / 伪人等资源 |
| **P5** | **优化主页面背景**：保持 UI 不变，只改善背景氛围与视觉完整度 |
